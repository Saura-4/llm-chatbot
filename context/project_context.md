# LLM Chatbot Backend — Project Context

## Purpose
An LLM chatbot backend, built with production-grade practices: FastAPI,
JWT auth, Postgres, Redis, Docker, and SSE streaming. Portfolio-worthy on
its own merits.

## Learning approach
- Concepts explained first, then code given to type manually (not copy-paste)
  into the editor — typing builds retention.
- Priority is understanding, not speed. Developer will explicitly push back
  if a session drifts toward code before he's built real familiarity with a
  new concept/API surface — treat this as a hard rule, not a preference to
  be balanced against pace.
- Full request-flow mental model reinforced every session: request →
  validation gate → business logic → response. Not isolated code explanations.
- Developer wants to learn broadly around a topic, not just the minimum
  needed to write the next function — it's fine to cover more than gets
  directly used in code, as long as it's genuinely related to the concept
  at hand.
- Concepts should be learned through reasoning, prediction, and questioning
  before implementation. Code is only introduced once the underlying mental
  model is solid.

## Alembic (conceptually mastered)
- SQLAlchemy models describe the desired schema but do not modify existing database tables.
- `Base.metadata.create_all()` creates missing tables only; it never alters existing tables.
- Alembic exists to manage explicit, version-controlled schema evolution.
- Alembic stores schema evolution as a chain of migration revisions.
- `alembic_version` stores the current revision applied to a database.
- `alembic upgrade <target>` applies only the missing revisions required to reach the target revision.
- `upgrade()` moves the schema forward and `downgrade()` attempts to reverse that migration.
- Destructive migrations may restore schema during downgrade but cannot automatically restore deleted data.
- `Base.metadata` is an in-memory schema description built from imported SQLAlchemy models.
- Alembic compares `Base.metadata` with the live PostgreSQL schema during autogeneration.
- Alembic runs in a separate Python process from the FastAPI application, so models must be imported in the Alembic process to populate `Base.metadata`.
- Alembic trusts `Base.metadata` as the desired schema; missing model imports can therefore generate incorrect destructive migrations.
- Autogenerated migrations are drafts and must always be reviewed before execution.

## Chat architecture
- Database is the chatbot's memory.
- Every request reconstructs context from stored messages.
- LLMs are stateless.
- Conversation history is rebuilt before every LLM request.
- Message ordering is determined by timestamps.
- Future context optimizations (summarization, sliding window, RAG) understood conceptually but intentionally deferred.

## Schema design decisions
- Message content uses `Text`, not `String`.
- Conversation titles use `String`.
- `updated_at` exists for activity ordering.
- Database-generated timestamps are preferred over Python-generated timestamps.
- Enum is preferred over plain String for message roles to enforce valid values.
- `MessageRole` is designed to be extensible (e.g. SYSTEM, USER, ASSISTANT).

## Decisions
- bcrypt instead of passlib.
- JWT helper functions remain framework-agnostic.
- Authentication dependency separated into `dependencies.py`.
- Auto-login after signup.
- Conversation and Message use normalized relational tables rather than storing chat history in a single JSON/blob column.
- SQLAlchemy relationships are preferred over manual queries whenever navigating object graphs.
- Message roles will use SQLAlchemy Enum instead of String for stronger database integrity.
